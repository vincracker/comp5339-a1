## Project structure

```
code/
├── main.py          # runs the four stages end to end
├── src/
│   ├── acquisition/   # Task 1 -- TfNSW chargers + ABS ASGS SA4 boundaries  [A]
│   ├── integration/   # Task 2 -- cleaning.py [B], spatial_join.py [C],
│   │                  #           quality.py [B]
│   ├── augmentation/  # Task 3 -- external attributes + matching            [D]
│   └── storage/       # Task 4 -- DuckDB load (spatial extension)           [D]
├── sql/schema.sql   # Task 4 -- DDL (deliverable)
├── notebooks/       # EDA and report figures -- see notebooks/README.md
├── data/
│   ├── raw/         # as downloaded -- IMMUTABLE, regenerated by script
│   ├── interim/     # cleaned / joined intermediates
│   ├── external/    # cached augmentation responses (committed)
│   └── processed/   # final tables + the .duckdb file
└── tests/
```

One package per assignment task, each exposing a `run()` entry point so stages can be
invoked individually while developing or driven end to end from `main.py`.
`integration/` is shared by B and C in **separate modules** (`cleaning.py`,
`spatial_join.py`) -- keep it that way so you are not editing the same file.

Pipeline logic lives in `src/`; notebooks explore and produce figures. See
`notebooks/README.md` for that boundary and why it exists.

The `data/` subdirectories hold a `.gitkeep` file because **git tracks files, not
directories** -- an empty folder does not survive a clone, so without them a fresh
checkout would be missing the paths the pipeline writes to. Each one also explains what
belongs in that directory and whether its contents are committed; worth reading before
putting a file somewhere. Delete a `.gitkeep` only once the directory holds something
tracked.

## Setup

There are two tracks, and they are not interchangeable.

**For the group (uv).** Fast, and `uv.lock` pins exact versions so all four of you run the
same environment:

```
uv sync
nbstripout --install     # once per clone, per member -- see notebooks/README.md
```

**For the marker (plain venv + pip).** The assignment requires the project to run "within a
clean Python virtual environment" from `requirements.txt`. Assume it will be built with
stdlib tooling, not uv:

```
python3 -m venv .venv && source .venv/bin/activate
pip install -r requirements.txt
```

`requirements.txt` is **generated**, never hand-edited. Regenerate it whenever a dependency
changes:

```
uv export --no-hashes --no-dev --format requirements-txt -o requirements.txt
```

`--no-hashes` matters: hash-pinned output makes plain `pip` far fussier. Verified to install
and run the pipeline in a clean `python3 -m venv` with stdlib pip only.

## Execution

Every stage exposes a `run()`, and `main.py` drives all four in order. That gives one command
for the marker and per-stage runs while developing -- acquisition and augmentation are slow, so
you will not want to re-run them on every change.

Full pipeline:

```
python main.py
```

A single stage, while developing:

```
python -c "import src.integration; src.integration.run()"
```
